MEGA FUTBOL - MODELO DE DATOS (SUPABASE / POSTGRES)
Spec 01 de 6 - requiere haber leido 00-vision-y-reglas-de-negocio.txt
=======================================================================

Todas las tablas viven en el schema "public" de Supabase, salvo
auth.users que ya la maneja Supabase por su cuenta. Los ids son uuid
(gen_random_uuid() o el default de Supabase) salvo que se indique otra
cosa.

TABLA: usuario  (extiende a auth.users, no la reemplaza)
-----------------------------------------------------------
- id                uuid, PK, references auth.users(id) on delete cascade
- nombre            text, not null
- telefono          text, nullable
- created_at        timestamptz, default now()
- inasistencias     int, not null, default 0    -- del ciclo actual;
                      persistente a proposito, NO se calcula contando
                      reservas no_show (ver abajo)
- suspensiones      int, not null, default 0    -- cuantas cumplio
- suspendido_hasta  timestamptz, nullable       -- no puede reservar hasta aca
- vetado            boolean, not null, default false  -- veto permanente

Notas:
- El email y la contrasena los maneja Supabase Auth (auth.users), NO se
  duplican en esta tabla.
- Un trigger sobre auth.users (on insert) crea automaticamente la fila
  correspondiente en public.usuario, tomando el nombre de los metadatos
  del registro (raw_user_meta_data->>'nombre'). Esto es un patron
  estandar de Supabase (funcion handle_new_user() + trigger
  on_auth_user_created). Documentarlo en la migracion.
- Un empleado tambien es un usuario (ver tabla empleado). No hay tabla
  separada de "clientes".
- Los cuatro campos de amonestaciones (inasistencias, suspensiones,
  suspendido_hasta, vetado) son columnas y no consultas sobre reserva.
  Eso es lo que permite borrar las reservas viejas sin perder el
  historial de sanciones: las reservas se eliminan 15 dias despues de
  terminado el turno (ver spec 02, TAREAS PROGRAMADAS), y si el
  contador se calculara contando filas no_show, un usuario sancionado
  volveria a cero solo porque paso el tiempo.

TABLA: sede
------------
- id           uuid, PK
- nombre       text, not null           -- "San Justo" es el unico dato hoy
- direccion    text, nullable
- created_at   timestamptz, default now()

TABLA: cancha
--------------
- id            uuid, PK
- sede_id       uuid, FK -> sede.id, not null
- numero        int, not null
- capacidad     int, not null
- precio_base   numeric(10,2), not null   -- precio por turno de 1h, sin recargo
- activa        boolean, default true     -- para dar de baja una cancha sin borrarla
- constraint UNIQUE(sede_id, numero)

TABLA: bloqueo_cancha
----------------------
Fechas puntuales en las que una cancha no se puede reservar, sin darla
de baja del todo: mantenimiento, un torneo, un evento privado.

- id          uuid, PK
- cancha_id   uuid, FK -> cancha.id, not null, on delete cascade
- desde       date, not null
- hasta       date, not null    -- inclusive; un solo dia = desde = hasta
- motivo      text, nullable
- creado_por  uuid, FK -> empleado.id, nullable
- created_at  timestamptz, not null, default now()
- constraint desde <= hasta
- Indice en (cancha_id, desde, hasta) para la consulta de disponibilidad.

Diferencia con cancha.activa: `activa` es un interruptor permanente que
saca la cancha del mapa hasta nuevo aviso; un bloqueo es acotado a
fechas y no cambia nada fuera de ellas. Un bloqueo cubre el dia entero:
no se bloquean turnos sueltos (para eso el staff puede reservar el
turno).

Se escribe solo con bloquear_cancha / desbloquear_cancha, ambas de
admin (ver spec 02). Lectura publica, para poder explicar por que un
dia no tiene turnos.

TABLA: reserva
---------------
- id                    uuid, PK
- cancha_id             uuid, FK -> cancha.id, not null
- usuario_id            uuid, FK -> usuario.id, not null
- fecha                 date, not null
- hora_inicio           time, not null       -- hora_fin se calcula como +1h, no se guarda
- precio_total          numeric(10,2), not null   -- calculado en la funcion crear_reserva, YA con recargo si aplica
- monto_sena            numeric(10,2), not null, default 15000
- estado                text, check in ('pendiente_pago','confirmada','cancelada','completada','no_show')
- llegada_validada_at   timestamptz, nullable
- llegada_validada_por  uuid, FK -> empleado.id, nullable
- cancelada_at          timestamptz, nullable
- cancelada_por         uuid, FK -> empleado.id, nullable
- no_show_at            timestamptz, nullable    -- cuando se marco la inasistencia
- no_show_por           uuid, FK -> empleado.id, nullable
- sena_devuelta         boolean, default false   -- registro manual de que el staff devolvio la sena
- created_at            timestamptz, default now()

Constraints importantes:
- UNIQUE INDEX parcial en (cancha_id, fecha, hora_inicio) para toda
  reserva cuyo estado NO sea 'cancelada'. Evita que dos reservas
  activas ocupen el mismo turno de la misma cancha, incluso si dos
  requests llegan al mismo tiempo (esto lo garantiza Postgres, no hace
  falta logica extra en el frontend).
  Ejemplo: create unique index reserva_turno_unico on reserva
  (cancha_id, fecha, hora_inicio) where estado <> 'cancelada';
- UNIQUE INDEX parcial en (usuario_id, fecha, hora_inicio) con el mismo
  criterio: un usuario no puede tener dos reservas activas a la misma
  fecha y hora (no puede jugar en dos canchas a la vez).
  create unique index reserva_usuario_horario_unico on reserva
  (usuario_id, fecha, hora_inicio) where estado <> 'cancelada';
- Indice en (cancha_id, fecha) para consultas de disponibilidad rapidas.
- IMPORTANTE (ver spec 02): los roles "authenticated" y "anon" NO tienen
  permiso de INSERT/UPDATE directo sobre esta tabla. Toda escritura pasa
  por las funciones crear_reserva, confirmar_reserva, validar_llegada y
  cancelar_reserva.

TABLA: configuracion  (fila unica)
----------------------------------------
Los parametros del negocio: antes eran funciones SQL fijas y cambiarlos
era escribir una migracion. Ahora son datos, porque el panel de admin
los edita.

- id                        boolean, PK, default true, check (id)
                              -- garantiza una sola fila
- hora_primer_turno         time, not null, default '08:00'
- hora_ultimo_turno         time, not null, default '22:00'
- hora_recargo_desde        time, not null, default '19:00'
- factor_recargo            numeric(4,2), not null, default 1.10
- monto_sena                numeric(10,2), not null, default 15000
- max_reservas_activas      int, not null, default 3
- dias_anticipacion_max     int, not null, default 30
- dias_retencion_reservas   int, not null, default 15
                              -- dias que se conserva una reserva
                                 despues de que termino el turno
- inasistencias_aviso       int, not null, default 2
- inasistencias_suspension  int, not null, default 5
- meses_suspension          int, not null, default 2
- actualizado_at            timestamptz, not null, default now()
- actualizado_por           uuid, FK -> empleado.id, nullable

Tiene checks que impiden dejarla en un estado absurdo (primer turno
antes del ultimo, recargo >= 1, seña > 0, umbral de suspension mayor al
de aviso, etc.).

Las funciones hora_primer_turno(), monto_sena_default() y companía
siguen existiendo con el mismo nombre y la misma firma: ahora leen esta
tabla. Por eso dejaron de ser IMMUTABLE y pasaron a STABLE.

TABLA: pago  (FASE 2 EN PAUSA - existe en el esquema, nadie la escribe)
-------------------------------------------------------------------------
- id                    uuid, PK
- reserva_id            uuid, FK -> reserva.id, not null, unique
- mp_payment_id         text, nullable    -- id que devuelve Mercado Pago
- monto                 numeric(10,2), not null   -- 15000
- estado                text, check in ('pendiente','aprobado','rechazado','expirado')
- fecha_pago            timestamptz, nullable
- comprobante_enviado   boolean, default false
- comprobante_email     text   -- copia del email al momento del pago
- created_at            timestamptz, default now()

Esta tabla solo la escribe la Edge Function del webhook de Mercado Pago,
usando la service role key (que ignora RLS). Ningun cliente (anon ni
authenticated) escribe en pago directamente.

NOTAS DE DISENO
-----------------
- precio_total se calcula y se guarda en el momento de crear la
  reserva (dentro de la funcion crear_reserva), no se recalcula
  despues. Asi, si cambia el precio_base de una cancha mas adelante,
  las reservas viejas no se ven afectadas.

- El estado 'pendiente_pago' deberia expirar solo despues de un tiempo
  razonable si no hay pago confirmado (sugerido: 15 minutos), liberando
  el turno. Esto tiene sentido implementarlo junto con la Fase 2 (pago
  real), por ejemplo con un cron de Supabase (pg_cron o una Edge
  Function programada) que cancele las reservas vencidas.

- Todas las fechas y horas se guardan y se comparan asumiendo
  America/Argentina/Buenos_Aires (ver spec 00, regla 12). Configurar el
  timezone de la base o convertir explicitamente en las funciones.

- El campo "rol" en empleado no debe usarse todavia para bloquear
  ninguna accion: hoy cualquier fila en empleado alcanza para tener
  acceso completo al panel de staff (ver spec 04).

DATOS INICIALES (SEED) - CANCHAS DE SAN JUSTO
--------------------------------------------------
Datos reales confirmados por Federico. Van todas con sede_id = San
Justo, activa = true. El campo capacidad es la cantidad total de
jugadores del partido (no por equipo).

Total: 20 canchas

  cantidad | numeros reales        | capacidad | precio_base
  ---------|-----------------------|-----------|-------------
  6        | 7, 8, 9, 10, 11 y 20  | 10        | $40.000   (fútbol 5)
  4        | 12 a 15               | 12        | $52.000   (fútbol 6)
  6        | 1 a 6                 | 14        | $60.000   (fútbol 7)
  4        | 16 a 19               | 16        | $72.000   (fútbol 8)

Ojo: la numeracion del seed original de este spec era inventada
(agrupaba los numeros por modalidad en bloques ordenados). La de arriba
es la real del predio, la misma que usan los bocetos, y quedo corregida
en la migracion numeracion_real_de_canchas. Los numeros NO son
correlativos por modalidad: la cancha 20 es de futbol 5, no de futbol 8.

Nota: la "modalidad" (fútbol 5/6/7/8) hoy se puede derivar de la
capacidad uno a uno (10→5, 12→6, 14→7, 16→8), así que no hace falta
una columna aparte para el MVP. Si mas adelante se quiere mostrar la
etiqueta "Fútbol 6" directamente en el front sin calcularla, se puede
agregar una columna `modalidad text` a la tabla cancha en una
migracion nueva — no rompe nada de lo ya definido.

Nota de negocio (cierra el punto abierto de la regla 5 del spec 00):
con estos precios reales, el precio_base mínimo es $40.000, siempre
por encima de la seña de $15.000 — el caso "seña mayor al precio
total" no se da con las canchas actuales.
