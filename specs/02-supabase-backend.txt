MEGA FUTBOL - BACKEND EN SUPABASE (RLS, FUNCIONES Y EDGE FUNCTIONS)
Spec 02 de 6 - requiere haber leido 00 y 01
======================================================================

PRINCIPIO GENERAL
--------------------
No hay servidor propio. El frontend usa @supabase/supabase-js
directamente contra el proyecto de Supabase. La seguridad vive en la
base de datos:

- Lecturas y escrituras simples (leer canchas, leer mi perfil) se
  resuelven con Row Level Security (RLS) sobre las tablas.
- Escrituras con logica de negocio (crear una reserva, validar
  llegada, cancelar) se resuelven con funciones de Postgres (RPC),
  llamadas desde el frontend con supabase.rpc('nombre_funcion', {...}).
- Lo que necesita un secreto que nunca debe llegar al navegador
  (token de Mercado Pago, API key del servicio de mail) se resuelve
  con Edge Functions.

AUTENTICACION
---------------
Se usa Supabase Auth con email + password:
- Registro: supabase.auth.signUp({ email, password, options: { data:
  { nombre, telefono } } })  -- nombre y telefono viajan en los
  metadatos y el trigger on_auth_user_created los copia a
  public.usuario. El telefono es OBLIGATORIO en el formulario de
  registro (el staff lo necesita para contactar al usuario), aunque la
  columna siga siendo nullable para usuarios creados desde el dashboard.
- Login: supabase.auth.signInWithPassword({ email, password })
- Sesion: supabase-js maneja el token y el refresh solo.
- Para saber si el usuario logueado es empleado (y de que sede), se
  puede exponer una funcion auxiliar:
    function mi_empleado() -- SECURITY INVOKER
      returns table(empleado_id uuid, sede_id uuid)
      as $$ select id, sede_id from empleado
             where usuario_id = auth.uid() and activo $$;

ROW LEVEL SECURITY POR TABLA
--------------------------------
usuario:
  - SELECT: auth.uid() = id (cada uno ve/edita solo su propio perfil)
            OR el que consulta es empleado de la sede donde ese usuario
               tiene alguna reserva (para que la agenda del staff pueda
               mostrar nombre y telefono, ver spec 04). Un empleado NO
               ve usuarios que nunca reservaron en su sede.
  - UPDATE: auth.uid() = id (solo nombre y telefono)
  - INSERT: solo la via el trigger (no hace falta policy de insert para
    el cliente)

sede, cancha, configuracion, bloqueo_cancha:
  - SELECT: true para todos (incluido anon) -- navegacion publica
  - INSERT/UPDATE/DELETE: sin policy para anon/authenticated y sin
    privilegios de escritura. sede se administra por migracion; el
    precio y el alta/baja de una cancha se cambian con
    actualizar_cancha, y los parametros globales con
    actualizar_configuracion, las dos solo para rol admin.

reserva:
  - SELECT: auth.uid() = usuario_id
            OR existe una fila en empleado con usuario_id = auth.uid()
               y empleado.sede_id = (select sede_id from cancha where
               cancha.id = reserva.cancha_id)
    (es decir: el dueno de la reserva, o cualquier empleado de la sede
    de esa cancha)
  - INSERT/UPDATE: SIN policy para anon/authenticated. Se revocan los
    privilegios de INSERT/UPDATE sobre la tabla para esos roles
    (revoke insert, update on reserva from authenticated, anon). Toda
    escritura pasa por las funciones de abajo, que corren como
    SECURITY DEFINER.

empleado:
  - SELECT: auth.uid() = usuario_id (cada empleado puede confirmar que
    el mismo es staff; no hace falta que vean la lista de otros
    empleados para el MVP)

pago (fase 2):
  - SELECT: mismo criterio que reserva (dueno o staff de la sede),
    uniendo por reserva_id
  - INSERT/UPDATE: ninguna policy para anon/authenticated. Solo la
    Edge Function del webhook escribe aca, usando la service role key
    (que ignora RLS por completo).

FUNCIONES DE POSTGRES (RPC)
-------------------------------
Todas SECURITY DEFINER (corren con permisos elevados, pero validan
"a mano" quien puede hacer que):

PARAMETROS DE NEGOCIO: los numeros de las reglas no se repiten como
literales dentro de cada funcion. Viven en la tabla configuracion (una
sola fila, ver spec 01) y se leen con funciones que conservan el mismo
nombre y la misma firma de siempre: hora_primer_turno,
hora_ultimo_turno, dias_anticipacion_max, max_reservas_activas,
hora_recargo_desde, factor_recargo, monto_sena_default. El precio se
calcula en un unico lugar, precio_turno().

Los edita el admin desde el panel, via actualizar_configuracion. Como
ahora dependen de una tabla, esas funciones son STABLE y ya no
IMMUTABLE.

1) disponibilidad(p_cancha_id uuid, p_fecha date)
   returns table(hora_inicio time, ocupado boolean, precio numeric)
   - Genera los turnos de 1 hora del dia, en punto, de 08:00 a 23:00
     (primer turno 08:00, ultimo 22:00), igual todos los dias.
   - "ocupado" es true si el turno tiene una reserva activa (estado <>
     'cancelada'), si ya paso (turnos de hoy mas temprano que la hora
     actual), o si esa cancha tiene un bloqueo que cubre esa fecha (ver
     bloqueo_cancha en el spec 01; un dia bloqueado devuelve todos los
     turnos ocupados). Para el que reserva son todos el mismo caso.
   - Calcula el precio de cada turno: precio_base, +10% si
     hora_inicio >= '19:00'.
   - Rechaza fechas pasadas y fechas a mas de 30 dias.
   - No requiere login (accesible por anon).

2) crear_reserva(p_cancha_id uuid, p_fecha date, p_hora_inicio time)
   returns reserva
   - Requiere auth.uid() no nulo (si es null, lanzar excepcion).
   - Busca precio_base de la cancha.
   - Calcula precio_total (con recargo si corresponde) y fija
     monto_sena en 15000.
   - Rechaza si el usuario esta vetado, o suspendido por inasistencias
     (mensaje con la fecha hasta la que dura). Se valida ACA, no en el
     frontend, porque es la unica via de escritura sobre reserva.
   - Rechaza: horarios que no sean un turno valido (en punto, 08:00 a
     22:00), turnos que ya pasaron, fechas a mas de 30 dias y canchas
     con activa = false.
   - Tope: un usuario puede tener hasta 3 reservas activas
     ('pendiente_pago' o 'confirmada') a futuro. Las ya jugadas no
     cuentan, para que no lo bloqueen para siempre.
   - Un usuario no puede tener dos reservas activas a la misma fecha y
     hora (no puede jugar en dos canchas a la vez). En dias distintos
     si puede repetir horario.
   - Inserta la reserva con usuario_id = auth.uid() y estado inicial
     'pendiente_pago' (ver spec 03 para como se trata ese estado en el
     MVP, antes de tener pagos reales).
   - Los dos casos de choque los garantizan unique indexes parciales de
     la tabla: capturar el error de Postgres y relanzar un mensaje
     claro ("Ese turno ya fue reservado" / "Ya tenes una reserva para
     ese dia y ese horario").

3) validar_llegada(p_reserva_id uuid)
   returns void
   - Verifica que auth.uid() pertenezca a un empleado de la misma sede
     que la cancha de esa reserva (si no, lanzar excepcion de permiso).
   - Actualiza llegada_validada_at = now(), llegada_validada_por = id
     del empleado que llama.

4) cancelar_reserva(p_reserva_id uuid, p_sena_devuelta boolean)
   returns void
   - Mismo chequeo de "es empleado de esa sede" que validar_llegada.
   - Actualiza estado = 'cancelada', cancelada_at = now(),
     cancelada_por = id del empleado, sena_devuelta = p_sena_devuelta.
   - Al pasar a 'cancelada', el indice unico parcial deja de contar esa
     fila, asi que el turno queda libre automaticamente para una nueva
     reserva.

5) confirmar_reserva(p_reserva_id uuid)
   returns void
   - Mismo chequeo de "es empleado de esa sede" que validar_llegada.
   - Solo acepta reservas en 'pendiente_pago'; las pasa a 'confirmada'.
   - Es el puente manual mientras no hay Mercado Pago: el usuario
     transfiere la sena por fuera del sistema, el empleado la verifica
     y confirma desde el panel (ver spec 03). En la Fase 2 convive con
     el webhook, que hace lo mismo pero automatico.

6) marcar_inasistencia(p_reserva_id uuid)
   returns void
   - Mismo chequeo de "es empleado de esa sede": cualquier empleado
     puede marcarla, no hace falta ser admin.
   - Rechaza si la reserva esta cancelada, si ya estaba marcada, si
     tiene la llegada validada (el usuario si se presento) o si el
     turno todavia no empezo.
   - Pasa la reserva a 'no_show' y guarda no_show_at / no_show_por.
   - Suma 1 al contador del usuario y, si llego al umbral, aplica la
     sancion que corresponda (ver spec 04).

7) levantar_sancion(p_usuario_id uuid)   -- SOLO ADMIN
   returns void
   - Deja la cuenta como nueva: contador en 0, sin suspension, sin
     veto, y olvida las suspensiones cumplidas. Para revertir un error
     del staff o resolver un reclamo.

8) actualizar_configuracion(...)   -- SOLO ADMIN
   returns configuracion
   - Cambia los parametros globales. Los argumentos en NULL dejan el
     valor que ya estaba. Los checks de la tabla impiden guardar una
     combinacion invalida.

9) actualizar_cancha(p_cancha_id, p_precio_base, p_activa)  -- SOLO ADMIN
   returns cancha
   - Cambia el precio base y/o da de alta o de baja una cancha. No
     toca las reservas ya hechas: su precio quedo congelado. Dar de
     baja tampoco cancela sus reservas futuras, solo impide tomar
     turnos nuevos.

10) actualizar_canchas_sede(p_sede_id, p_activa)   -- SOLO ADMIN
    returns int (cuantas cambiaron)
    - Da de alta o de baja TODAS las canchas de la sede de una vez, en
      una sola operacion atomica. Mismas reglas que actualizar_cancha:
      no cancela reservas ya hechas.

11) es_admin()
    returns boolean
    - SECURITY DEFINER. El chequeo de rol admin en un solo lugar, igual
      que es_empleado_de_sede para el staff.

12) bloquear_cancha(p_cancha_id, p_desde, p_hasta, p_motivo, p_forzar)
    -- SOLO ADMIN
    returns bloqueo_cancha
    - Saca una cancha de circulacion entre dos fechas (p_hasta en null
      = un solo dia). Rechaza rangos invertidos, rangos que ya pasaron
      y canchas inexistentes.
    - Si hay reservas activas en el rango NO bloquea: avisa cuantas
      son. Con p_forzar => true bloquea igual y las deja en pie, para
      que el staff las resuelva a mano (mismo criterio que dar de baja
      una cancha: el sistema no cancela ni devuelve plata solo).

13) desbloquear_cancha(p_bloqueo_id)   -- SOLO ADMIN
    returns void
    - Levanta un bloqueo. Los turnos de esas fechas vuelven solos.

14) mi_empleado()  -- SECURITY INVOKER, ver AUTENTICACION arriba.
    Devuelve empleado_id, sede_id y rol.

15) ocupacion_del_dia(p_sede_id uuid, p_fecha date)
    returns table(cancha_id uuid, turnos_totales int,
                  turnos_libres int, turnos_reservados int)
    - El resumen que necesita el mapa, en una sola consulta en vez de
      una por cancha. No requiere login.
    - Reusa disponibilidad() por dentro, asi que el criterio de "libre"
      es el mismo que ve el usuario al abrir una cancha.
    - turnos_libres y turnos_reservados NO son lo mismo: un turno deja
      de estar libre si esta reservado, si ya paso o si la cancha esta
      bloqueada ese dia; turnos_reservados cuenta solo reservas
      activas. El mapa usa libres = 0 para pintar la cancha de gris
      (completa) y reservados/totales para elegir el color de las que
      si tienen lugar (hasta 30% verde, mas de 30% amarillo, mas de
      70% rojo). Con un solo numero, una cancha sin reservas se veria
      llena al final del dia solo porque sus turnos ya pasaron.

No hay pantalla para los bloqueos todavia: se invocan las funciones.
El chequeo de admin es el mismo que para precios y configuracion,
porque bloquear fechas es una decision de negocio y no una tarea
operativa del dia a dia.

validar_llegada NO cambia el estado de la reserva: solo sella la
llegada. Los estados 'completada' y 'no_show' estan definidos en el
modelo pero todavia ninguna funcion los escribe.

EDGE FUNCTIONS (fase 2, Deno/TypeScript en supabase/functions/)
--------------------------------------------------------------------
EN PAUSA, SIN FECHA: ninguna de estas dos existe en el repo. El
proyecto es una pieza de portfolio y se decidio no integrar pagos
reales (ver spec 00, CONTEXTO DEL PROYECTO, y spec 03). Queda escrito
como referencia.

1) crear-preferencia-pago
   - La llama el frontend (usuario autenticado) pasando reserva_id.
   - Usa el MERCADOPAGO_ACCESS_TOKEN (guardado como secreto de
     Supabase, nunca en el frontend) para crear una preferencia/QR de
     pago por el monto_sena de esa reserva.
   - Devuelve al frontend los datos necesarios para mostrar el QR.

2) webhook-mercadopago
   - Endpoint publico que Mercado Pago llama cuando cambia el estado
     de un pago. Verifica que la notificacion sea autentica (firma /
     validacion segun la documentacion de Mercado Pago).
   - Si el pago fue aprobado: usa el cliente de Supabase con la
     service role key (bypassea RLS) para (a) insertar/actualizar la
     fila en pago, (b) pasar la reserva asociada a estado
     'confirmada'.
   - Dispara el envio del comprobante por mail (puede ser en la misma
     funcion o llamando a otra) usando el proveedor de mail elegido
     (ver spec 05) y marca comprobante_enviado = true en pago.

FLUJO DE TRABAJO CONTRA SUPABASE EN LA NUBE
-----------------------------------------------
Se trabaja directo contra el proyecto en la nube, sin stack local ni
Docker. Los comandos se corren con `npx supabase ...` (ver spec 05).

Una sola vez por maquina:
- supabase login                    -- abre el navegador y guarda un token
                                        de acceso de la cuenta de Supabase
- supabase link --project-ref btnfakfcyqccgshpmzrp
                                     -- conecta el repo al proyecto; pide la
                                        password de la base de datos
                                        (Project Settings > Database)

Ciclo de cada cambio de esquema:
- supabase migration new <nombre>   -- crea un archivo SQL vacio en
                                        supabase/migrations/
- supabase db push --dry-run        -- muestra que migraciones se
                                        aplicarian, sin tocar nada
- supabase db push                  -- aplica las migraciones pendientes al
                                        proyecto en la nube
- supabase migration list           -- compara las migraciones del repo con
                                        las ya aplicadas en la nube

IMPORTANTE: una migracion que ya se aplico con `db push` NO se edita.
Si hay que corregir algo, se crea una migracion nueva que lo arregle.
Como no hay base local descartable, `db reset` no forma parte del
flujo: resetear seria borrar los datos reales del proyecto.

Edge Functions (fase 2):
- supabase functions new <nombre>   -- crea una Edge Function nueva
- supabase functions deploy <nombre> -- la sube al proyecto
- supabase secrets set NOMBRE=valor -- carga un secreto (token de Mercado
                                        Pago, API key de mail) para las
                                        Edge Functions

Opcional, solo si se instala Docker Desktop: `supabase start` levanta un
stack local descartable, `supabase db reset` le aplica todas las
migraciones desde cero y `supabase functions serve` corre las Edge
Functions en local.

Cada tabla, policy y funcion de este spec debe quedar como una
migracion SQL versionada en supabase/migrations/, no aplicada a mano
desde el dashboard, para que el esquema completo se pueda reconstruir
desde el repo en cualquier momento.
